# Baseline Screenshots

This directory contains golden reference screenshots for visual regression testing.

## Directory Structure

```
screenshots/
├── baseline/
│   ├── v1/          # Legacy UI baselines (frozen at weight-tracker-v1-ui tag)
│   └── v2/          # Redesign UI baselines (after v2 implementation complete)
├── test-results/    # Latest test run screenshots (generated by Playwright)
└── diffs/           # Visual difference images (if tests fail)
```

## Purpose

Baseline screenshots serve as the "golden" reference for what the UI should look like. Visual regression tests compare new screenshots against these baselines to detect unintended UI changes.

## How to Capture Baseline Screenshots (v2)

### Prerequisites

1. **v2 UI must be fully implemented** based on `docs/design/generated/weight-tracker-spec-v1.json`
2. **Code review passed** confirming design spec compliance
3. **Manual QA passed** verifying UI matches Figma design

### Step 1: Start Development Server

```bash
cd software-factory/generated-apps/weight-tracker-nextjs
npm run dev
```

Wait for server to start on `http://localhost:3000`.

### Step 2: Run Visual Tests

```bash
npm run test:visual
```

This will:
- Launch Playwright in headless mode
- Navigate to all screens (Splash, Login, Dashboard, History, Log Entry, Analytics, Settings)
- Capture screenshots at 3 viewport sizes (mobile 375x667, tablet 768x1024, desktop 1440x900)
- Save screenshots to `screenshots/test-results/`

### Step 3: Verify Screenshots

Manually inspect generated screenshots in `screenshots/test-results/`:
- Check that all screens loaded correctly
- Verify no loading spinners or error states
- Confirm UI matches Figma design
- Ensure consistent styling across viewports

### Step 4: Promote to Baseline

Once screenshots are verified:

```bash
# Move screenshots to baseline/v2/
mv screenshots/test-results/*.png screenshots/baseline/v2/

# Alternatively, copy if you want to keep test results
cp screenshots/test-results/*.png screenshots/baseline/v2/
```

### Step 5: Compute Baseline Hash

```bash
node scripts/check-design-version.js --compute-baseline
```

This will:
- Compute MD5 hashes of all PNG files in `baseline/v2/`
- Concatenate the hashes
- Output a SHA256 hash of the concatenated result

Example output:
```
✅ Baseline hash computed successfully:

   a1b2c3d4e5f6...

Update design_version.json with:
  "baseline_hash": "a1b2c3d4e5f6..."
```

### Step 6: Update Design Version Manifest

Edit `design_version.json`:

```json
{
  "design_version": "v2",
  "spec_hash": "<computed SHA256 of spec file>",
  "baseline_hash": "<hash from step 5>",
  "status": "implemented",
  "last_updated": "<current date>"
}
```

### Step 7: Validate

```bash
node scripts/check-design-version.js
```

Should output:
```
✅ ALL CHECKS PASSED
Design artifacts are valid and ready for QA/deployment.
```

## Updating Baselines

Baselines should be updated only when **intentional** UI changes are made:

### When to Update

✅ **Update baselines when:**
- Design spec is updated with new Figma design
- Visual bugs are fixed and new appearance is correct
- Accessibility improvements change visual appearance
- Typography, colors, or spacing are intentionally adjusted

❌ **Do NOT update baselines for:**
- Temporary workarounds or hacks
- Unintended visual regressions
- Code refactoring that should not affect UI
- Flaky tests or inconsistent rendering

### How to Update

1. Implement the UI changes
2. Run `npm run test:visual` to generate new screenshots
3. Manually verify the new screenshots match the intended design
4. Follow steps 4-7 above to promote to baseline and update hashes
5. Commit both the new screenshots and updated `design_version.json`
6. Document the change in git commit message

## File Naming Convention

Screenshots should follow this naming pattern:

```
<screen>-<viewport>-<width>x<height>.png
```

Examples:
- `splash-mobile-375x667.png`
- `dashboard-tablet-768x1024.png`
- `login-desktop-1440x900.png`
- `history-mobile-375x667.png`
- `log-desktop-1440x900.png`
- `analytics-tablet-768x1024.png`
- `settings-desktop-1440x900.png`

Expected files in `baseline/v2/`:
- 7 screens × 3 viewports = **21 screenshots total**

## Troubleshooting

### Screenshots are blank or show loading states

**Problem**: Tests ran before page fully loaded.
**Solution**: Increase wait time in Playwright spec, or add explicit wait for content to appear.

### Screenshots vary between runs (flaky)

**Problem**: Dynamic content (timestamps, random data) causes differences.
**Solution**: Mock dynamic data or use fixed test data in visual tests.

### Hash mismatch even though screenshots look identical

**Problem**: Image metadata or timestamps differ.
**Solution**: Ensure PNG files are saved without metadata. Use consistent compression settings.

### Baseline directory is empty

**Problem**: Forgot to capture baseline screenshots.
**Solution**: Follow "How to Capture Baseline Screenshots" steps above.

## CI/CD Integration

### Blocking QA/Deployment

The `check-design-version.js` script will block QA runs if:
- Design version manifest is missing
- Spec hash is `<TBD>` or mismatched
- Baseline directory is empty or hash is `<TBD>`
- Implementation status is `pending_implementation`

### GitHub Actions Workflow

A CI workflow will:
1. Run `node scripts/check-design-version.js`
2. If exit code is 0, proceed to visual tests
3. If exit code is 1, fail the build with clear error message

## Maintenance

### Regular Tasks

- **After design updates**: Re-capture baselines and update hashes
- **After dependency updates**: Verify screenshots haven't changed unexpectedly
- **Quarterly**: Review baseline screenshots for obsolete test cases

### Archiving Old Baselines

When a major redesign happens:
1. Rename `baseline/v2/` to `baseline/v2-archived-<date>/`
2. Create new `baseline/v3/` directory
3. Update `design_version.json` to `v3`
4. Capture new baselines
